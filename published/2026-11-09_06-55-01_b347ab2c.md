**🤖 AI Engineering Digest — главное за неделю**

📅 **Период: 2–8 ноября 2026**

На этой неделе особенно интересны исследования о том, как Coding Agents соблюдают инструкции и что происходит, когда агенты начинают автоматически улучшать собственные Skills.

Параллельно GitHub добавила метрики полезности AI Code Review и поддержку обновления агентных пакетов через Dependabot.

Главная тенденция:

**AI-агентов начинают разрабатывать и эксплуатировать как полноценные программные компоненты.**

С версиями, тестами, метриками качества и контролем изменений.


**1. AGENTS.md — формулировка правил действительно влияет на Coding Agent**

3 ноября опубликовано исследование Do Coding Agents Follow AGENTS.md?

Авторы проверили:

— 86 задач
— 4 варианта формулировки правил
— 4 комбинации моделей и agent harness

Выяснилось, что условные инструкции соблюдались хуже, чем предписывающие и объясняющие.

Например:

«Если изменяется публичный API, желательно проверить совместимость».

Такая формулировка может восприниматься агентом как необязательная рекомендация.

Более определённая:

«При изменении публичного API обязательно запусти проверку совместимости. Если она недоступна, сообщи об этом».

Но даже правильно написанная инструкция не гарантирует выполнения.

Поэтому:

**AGENTS.md ≠ Policy Engine**

Практический вывод — разделять правила:

— рекомендации → AGENTS.md
— обязательные практики → AGENTS.md + Review
— критичные ограничения → CI Policy

Получается:

AGENTS.md → Coding Agent → Verification → Policy Gate → Merge

Особенно интересно, что универсального лучшего стиля инструкций исследование не обнаружило.

Значит, AGENTS.md стоит тестировать на конкретных моделях и задачах.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** исследование, можно пилотировать

[Исследование — Do Coding Agents Follow AGENTS.md?](https://arxiv.org/abs/2611.04367)


**2. Самообучающиеся агенты могут забывать старые навыки**

2 ноября вышло исследование Can Coding Agents Sustain Continual Evolution without Forgetting?

Авторы проверили, что происходит, когда agent harness последовательно улучшают под разные классы задач.

Обнаружилась серьёзная проблема.

В одном эксперименте качество Meta-Harness на SWE-bench после оптимизации достигло 94%.

Но после дальнейшей адаптации на FeatureBench упало до 32% к пятому раунду.

Это результат конкретного эксперимента, а не универсальная оценка.

Однако проблема принципиальная.

**Новый Skill ≠ Улучшенный Agent**

Представим Architecture Review Agent.

Он умеет проверять:

— обратную совместимость
— безопасность
— архитектурные ограничения
— качество тестов

Затем мы начинаем улучшать его под скорость ревью.

Он действительно становится быстрее.

Но постепенно перестаёт находить сложные проблемы совместимости.

Поэтому для Skills нужен собственный Regression Suite.

Workflow:

Skill Update → Evaluation Suite → Compare Baseline → Approve / Reject

Причём проверять необходимо не только новую задачу, ради которой изменяли Skill.

Нужно повторно запускать старые эталонные сценарии.

Это особенно важно для Repository Memory и автоматического обновления инструкций.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** исследование, доступен код

[Исследование — Continual Harness Evolution](https://arxiv.org/abs/2611.03219)

[GitHub — Continual Harness Evolution](https://github.com/THU-Agent/continual-harness-evolution)


**3. GitHub — AI Code Review наконец начинают измерять по результатам**

5 ноября GitHub расширила Copilot Usage Metrics API.

Теперь можно получать статистику не только о количестве AI Code Reviews.

Появились новые метрики:

— сколько замечаний оставил AI Reviewer
— на сколько замечаний отреагировали разработчики
— распределение замечаний по критичности
— типы замечаний
— какие Skills и MCP использовались
— сколько PR объединили без последующего запроса изменений от человека

Одна из ключевых метрик — Addressed Rate.

Addressed Rate = Addressed Comments / Evaluated Comments

Например:

AI Reviewer оставил 200 замечаний.

Разработчики отреагировали на 80.

Addressed Rate = 40%.

Но важный нюанс: GitHub считает замечание обработанным не только после исправления кода.

Поэтому:

**Addressed Rate ≠ Fixed Bugs Rate**

Для внутренней AI Platform полезнее измерять сразу несколько показателей:

— Addressed Rate
— Accepted Fix Rate
— False Positive Rate
— Review Rework

Особенно интересно, что статистику можно связывать с используемыми Skills и MCP.

Например, сравнивать качество Architecture Review Skill до и после обновления.

Это уже позволяет управлять развитием AI-инструментов на основе результатов, а не количества запусков.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** можно применять

[Источник — GitHub Code Review Metrics](https://github.blog/changelog/2026-11-05-usage-metrics-api-adds-code-review-details-and-addressed-rate/)


**4. Skills становятся управляемыми зависимостями**

3 ноября GitHub объявила поддержку Agent Package Manager в Dependabot.

Теперь Dependabot может предлагать обновления:

— Agent Skills
— prompts
— инструкций для агентов

Зависимости описываются в apm.yml.

Dependabot создаёт PR с обновлением и при наличии lock-файла обновляет apm.lock.yaml.

Пока поддерживаются обновления версий, но не security updates для APM.

Это интересный архитектурный сдвиг.

Раньше Skills часто представляли собой набор Markdown-файлов, которые вручную копировали между проектами.

Теперь их можно рассматривать как полноценные инженерные зависимости.

Например:

Platform Project → C++ Skill → Meson Skill → Release Skill

У каждого Skill появляются:

— владелец
— версия
— история изменений
— зависимости
— совместимость
— тесты

Получается:

Skill Registry → Versioned Skill → Dependency Update → Evaluation → MR

И здесь важно связать новость с предыдущим исследованием.

Автоматическое обновление Skill может ухудшить поведение агента.

Поэтому:

**Skill Update ≠ Safe Skill Update**

Перед принятием новой версии нужно запускать Agent Regression Suite.

🧪 **Зрелость:** можно применять

**5. Vibetrace — управление Coding Agent через Execution Traces**

3 ноября исследователи представили Vibetrace.

Это система визуализации и управления работой Coding Agents на базе OpenCode.

Она позволяет:

— видеть последовательность действий
— исследовать промежуточные состояния
— находить момент ошибки
— возвращаться к предыдущему шагу
— создавать альтернативную ветку выполнения
— превращать исправления в повторно используемые Skills

Авторы предлагают подход:

Observe → Understand → Intervene → Evolve

Например:

Coding Agent выполнил 40 шагов.

На шаге 32 принял неправильное архитектурное решение.

Обычно разработчик пишет в чат:

«Нет, переделай».

Но агент уже мог изменить множество файлов.

Vibetrace предлагает другой механизм:

Execution Trace → Select Checkpoint → Correct Decision → Resume

В эксперименте на SWE-bench Verified извлечённые Skills:

— сократили входные токены на 23%
— снизили стоимость на 15,5%
— повысили pass rate с 65% до 68%

Это результаты конкретного эксперимента.

Но сама идея очень интересна.

**Agent Execution ≠ Black Box**

Для долгоживущих агентов нужен не только чат.

Нужны:

— Execution Trace
— Checkpoints
— Intervention
— Recovery
— Reusable Knowledge

При этом внешние действия требуют отдельного контроля: возврат к checkpoint не отменяет автоматически созданный релиз или изменение в Jira.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** исследовательский прототип

[Исследование — Vibetrace](https://arxiv.org/abs/2611.04466)


**6. Step-Zero Attack — агент может навредить ещё до анализа данных моделью**

На границе отчётного периода опубликовано исследование Step-Zero Attack.

Авторы рассмотрели проблему безопасности при обработке недоверенных данных.

Например, агент получает архив и пытается его распаковать.

Опасное содержимое может вызвать чрезмерный расход ресурсов ещё до того, как LLM увидит результат.

В эксперименте:

— 7 agent harness
— 6 моделей
— 42 комбинации

В 32 комбинациях был превышен лимит дискового пространства 4 МиБ.

В 26 случаях это произошло до того, как модель увидела обработанные файлы.

Это показывает важное ограничение AI Security.

Обычно защита сосредоточена на prompt injection.

Но часть атак происходит на уровне инструментов и обработки входных данных.

Поэтому:

**Model Context Security ≠ Tool Execution Security**

Нужна архитектура:

Untrusted Input → Resource Limits → Sandbox → Validation → Agent Context

Для MCP и Tool Gateway это означает:

— ограничение размера данных
— лимиты CPU и памяти
— таймауты
— безопасную распаковку
— контроль путей записи
— ограничения файловой системы

Безопасность агента начинается раньше, чем модель получает контекст.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** исследование

[Исследование — Step-Zero Attack](https://arxiv.org/abs/2611.01953)


**💡 Что можно попробовать**

**1. AGENTS.md Compliance Tests**

Выбрать 10–15 инженерных правил.

Создать тестовые задачи, в которых агент должен продемонстрировать их соблюдение.

Проверить разные формулировки.

Результат — понимание, какие правила действительно работают.


**2. Agent Regression Suite**

Для каждого важного Skill подготовить набор эталонных задач.

После обновления запускать:

Skill Update → Tests → Compare Baseline → Approve

Результат — защита от деградации агента.


**3. AI Review Effectiveness Metrics**

Начать собирать:

— всего замечаний
— принято
— отклонено
— привело к исправлению
— ошибочные замечания

Результат — измерение пользы AI Review.


**4. Versioned Skills Registry**

Для внутренних Skills определить:

Skill ID → Version → Owner → Dependencies → Evaluation Results

Все обновления проводить через MR.

Результат — управляемые инженерные знания.


**5. Agent Execution Trace**

Для одного долгоживущего агента сохранять:

Task ID → Step → Tool Call → Result → Checkpoint

Начать без сложного UI.

Результат — более простое расследование ошибок и восстановление выполнения.


**Главный вывод недели**

AI Engineering постепенно приходит к тем же практикам, которые давно используются в обычной разработке ПО.

Теперь тестировать нужно не только код, но и Skills.

Версионировать — не только библиотеки, но и инструкции агентов.

Измерять — не количество AI-запусков, а качество результата.

А наблюдать — не только сервисы, но и выполнение Coding Agents.

Получается:

Requirements → Context → Versioned Skills → Agent → Execution Trace → Verification → Evaluation → Controlled Improvement
