**🤖 AI Engineering Digest — главное за неделю**

📅 **Период: 13–18 октября 2026**

На этой неделе сразу несколько интересных событий вокруг AI Engineering.

Microsoft развивает постоянных агентов с собственной памятью и правами, GitHub автоматизирует исправление уязвимостей, а Anthropic опубликовала исследование того, как AI меняет работу инженерных команд.

Но самое интересное — появляются новые ограничения.

Агенты могут выполнять всё больше работы, однако инфраструктура выполнения, безопасность и человеческая проверка становятся критически важными.


**1. Microsoft — Agent Identity + Process Memory**

Microsoft представила новые возможности Copilot Studio для постоянно работающих корпоративных агентов.

Теперь агент может иметь:

— собственную учётную запись
— собственные разрешения
— память между запусками
— автоматические триггеры
— историю выполнения процесса

Причём агент не обязательно принадлежит конкретному сотруднику.

Он может принадлежать организации и выполнять один и тот же процесс длительное время.

Например:

Release Agent → Check Jira → Check CI → Compare Previous State → Prepare Report

Важное архитектурное разделение:

Agent Identity ≠ User Identity

Process Memory ≠ Conversation History

Agent ≠ Process Owner

Ещё интереснее запланированный механизм Agent Refinements.

Microsoft хочет анализировать историю работы агентов и предлагать улучшения:

Repeated Actions → Workflow

Repeated Patterns → Skills

Ambiguous Instructions → Clarification

То есть Agent Platform постепенно начинает не только выполнять задачи, но и помогать совершенствовать собственные процессы.

Пока возможности постепенно развёртываются, часть механизмов ещё только анонсирована.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** раннее внедрение

[Источник — Microsoft: Persistent and proactive agents](https://www.microsoft.com/en-us/copilot/blog/copilot-studio/delegate-shared-business-processes-to-agents-that-are-more-persistent-and-proactive-with-microsoft-copilot-studio/)


**2. GitHub — Security Finding → Coding Agent → Verified Fix**

GitHub вывела Agentic Autofix в общую доступность.

Теперь обнаруженную уязвимость можно назначить Copilot как обычную задачу.

Агент:

— исследует связанные файлы
— определяет причину
— предлагает исправление
— повторно запускает CodeQL
— создаёт draft PR

Причём до 25 security alerts можно объединить в одну задачу.

Получается:

Security Alert → Coding Agent → Fix → CodeQL → PR → Human Review

Самое интересное здесь — независимая проверка.

Агент не просто сообщает, что исправил проблему.

Он повторно запускает анализатор, который обнаружил уязвимость.

GitHub также сделала общедоступным AI Scan для pull requests.

Он дополняет CodeQL и может находить проблемы в PHP, Bash, Terraform, Dockerfile и других технологиях.

При этом AI Scan не блокирует merge автоматически: его findings остаются рекомендациями.

Для внутренних платформ отсюда получается хороший pattern:

Deterministic Analysis + AI Analysis + Coding Agent + Verification + Human Review

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** можно применять

[Источник — GitHub Agentic Autofix](https://github.blog/changelog/2026-10-15-agentic-autofix-for-code-scanning-alerts-general-availability/)

**3. Anthropic — агенты начинают создавать новый bottleneck**

Anthropic опубликовала исследование собственной организации.

Одна из самых интересных цифр:

К августу AI-агенты, используемые отдельными сотрудниками, выполняли в шесть раз больше часов работы, чем сами сотрудники.

После внедрения coding agents инженеры стали создавать больше кода.

Но появилась новая проблема.

Человеческое внимание становится ограничением для обработки результатов агентов.

Представим:

Engineer
→ Agent A
→ Agent B
→ Agent C
→ Agent D

Каждый агент выполняет задачу.

Но все результаты требуют проверки.

И получается:

Agent Throughput ≠ Engineering Throughput

Если агентам можно поручить в десять раз больше задач, это ещё не означает десятикратного роста производительности команды.

Инженеры Anthropic уже создают дополнительные инструменты для наблюдения за агентами и управления их работой.

Для Engineering Management это важный сигнал.

Нужно измерять не только:

Agent Tasks Completed

Но и:

Agent Results → Review Queue → Rework → Accepted Changes

Возможно, одним из следующих ограничений AI-native SDLC станет именно человеческий Review Capacity.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** исследование реальной компании

[Исследование — How employment is changing at Anthropic](https://www.anthropic.com/research/employment-at-anthropic)


**4. Doc2Harness — AI пока плохо проектирует инфраструктуру для AI**

Вышло интересное исследование Doc2Harness.

Авторы решили проверить не то, насколько хорошо Coding Agent пишет прикладной код.

А насколько хорошо AI может создать сам Agent Harness.

То есть инфраструктуру, которая управляет:

— контекстом
— инструментами
— разрешениями
— сессиями
— ошибками
— выполнением команд

В исследовании участвовали 19 моделей.

Каждая должна была реализовать Harness по техническому описанию.

Результат лучшей модели — 53,05% успешно пройденных тестов.

Даже лучший результат означает провал почти половины сценариев.

Причём основные проблемы возникали не в отдельных компонентах, а на их пересечении.

Например:

Context Manager работает.

Tool Executor работает.

Permission Manager работает.

Но вместе они могут неправильно обрабатывать сложный сценарий.

Отсюда важный вывод для Agent Platform:

Harness ≠ просто набор MCP + Prompt + Tools

Это полноценная программная система.

И ей нужны:

Contract Tests → Integration Tests → Security Tests → Failure Injection → Evals

Особенно если сама инфраструктура тоже разрабатывается AI-агентами.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** research

[Исследование — Doc2Harness](https://arxiv.org/abs/2610.20344)


**5. LiteLLM — центральный AI Gateway становится критической точкой безопасности**

Check Point опубликовала подробный разбор уязвимостей LiteLLM.

LiteLLM часто используется как единая точка доступа к нескольким AI-провайдерам.

В ней находятся:

— API keys
— маршрутизация запросов
— настройки доступа
— бюджеты
— логи

Исследователи обнаружили проблемы, которые позволяли при определённых условиях получать административный доступ, читать файлы и перехватывать credentials.

Важно: исследование опубликовано сейчас, но обе описанные уязвимости уже исправлены в LiteLLM 1.83.9 и более поздних версиях.

Здесь интересен архитектурный вывод.

Мы часто обсуждаем безопасность:

Coding Agent → MCP → Sandbox

Но забываем ещё один критический компонент:

Agent → AI Gateway → Model Provider

Если Gateway скомпрометирован, могут пострадать сразу несколько AI-сервисов.

Поэтому корпоративному AI Gateway нужны:

RBAC + Secret Isolation + Network Policy + Audit + Version Control

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** исправления доступны

[Исследование — Check Point: LiteLLM](https://research.checkpoint.com/2026/when-llm-gateways-go-wrong-findings-from-litellm/)


**💡 Что можно попробовать**

**1. Persistent Process Memory**

Для одного повторяющегося процесса — например release checks — сохранять результаты предыдущих запусков отдельно от истории агента.

При новом запуске передавать только актуальное состояние и нерешённые вопросы.


**2. Agentic Security Remediation**

Связать:

Static Analysis → Coding Agent → Fix → Static Analysis → MR

Начать с типовых замечаний, которые легко проверить автоматически.


**3. Agent Review Queue**

Добавить метрики:

Agent Tasks Completed

Results Waiting for Review

Average Review Time

Rework Rate

Accepted Changes

Это позволит понять, не становится ли человеческая проверка ограничением для всей системы.


**4. AI Gateway Security Baseline**

Проверить:

— актуальность LiteLLM или другого gateway
— разграничение доступа
— хранение API keys
— ограничения сетевых запросов
— аудит административных операций


**5. Harness Integration Evals**

Проверять не только отдельные MCP tools, но и сложные сценарии:

Agent → Context → Permission → Tool → State Update

Особенно при ошибках сети, изменении разрешений и повторном выполнении операций.


**Главный вывод недели**

AI Engineering постепенно переходит от вопроса:

«Что агент умеет делать?»

к вопросу:

«Как организовать систему, в которой агент безопасно и эффективно выполняет работу?»

Для этого нужны:

Identity + Memory + Policy + Tools + Verification + Observability

Но появляется ещё один важный компонент:

Human Review Capacity.

Потому что количество выполненной агентами работы само по себе не означает, что команда способна превратить её в качественные изменения.

И целевая архитектура всё больше выглядит так:

Task → Process State → Agent → Policy → Tools → Verification → Human Review → State Update
