**🤖 AI Engineering Digest — главное за неделю**

📅 **Период: 9–15 ноября 2026**

На этой неделе главный инженерный тренд — переход от демонстраций возможностей AI-агентов к управлению их реальной работой.

GitLab предлагает проверять, когда агенту можно доверить самостоятельные действия. GitHub показывает, как создавать переносимые Skills. А новое исследование FlowPlan демонстрирует, что структурное планирование изменений способно существенно снизить стоимость Coding Agents.

Главный принцип:

**Agent Capability ≠ Permission to Act**

Умение выполнить задачу ещё не означает, что агенту нужно разрешать самостоятельно изменять систему.


**1. GitLab — AI-агент должен заслужить право на автономность**

9 ноября GitLab опубликовала методологию проведения AI-пилотов.

Основная идея довольно простая.

Вместо вопроса:

«Насколько впечатляюще агент справился с задачей?»

Нужно спрашивать:

«Какие доказательства необходимы, чтобы разрешить агенту самостоятельно выполнять этот workflow?»

Это важное изменение подхода к Agentic Development.

Например, хотим автоматизировать обновление платформенных библиотек.

Плохой вариант:

Jira → Coding Agent → GitLab → Merge

Более безопасный путь — постепенно расширять полномочия.

— Observe: агент читает данные и предлагает решение.
— Propose: готовит patch или MR, ничего самостоятельно не применяя.
— Execute with Approval: выполняет действие после подтверждения.
— Bounded Autonomy: самостоятельно действует только в разрешённых пределах.

При этом критерии перехода между уровнями нужно определить заранее.

Например, для автоматического обновления зависимости:

— 20 успешных проверок на эталонных проектах;
— отсутствие критичных ошибок;
— обязательная сборка и unit-тесты;
— возможность остановить выполнение;
— независимый контроль совместимости.

Это пример критериев, а не универсальный стандарт.

Самое важное — оценивать не качество текста агента, а результат его действий.

**Agent ≠ Policy Engine**

Агент может рекомендовать выполнение операции, но решение о разрешённых действиях должно оставаться за внешней системой.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** можно применять

**2. GitHub — переносимые Agent Skills становятся инженерными артефактами**

12 ноября GitHub опубликовала практическое руководство по созданию Agent Skills, которые можно повторно использовать в разных агентных инструментах.

Основная единица — версионируемый каталог с SKILL.md.

В нём описываются:

— когда применять Skill;
— какие шаги необходимо выполнить;
— какие ограничения учитывать;
— какие результаты должны получиться.

Интересен не сам Markdown-файл, а разделение ответственности.

Skill описывает процесс.

Agent Runtime предоставляет инструменты.

Tool Gateway управляет доступом.

Policy определяет разрешённые действия.

Например, можно создать единый Platform Update Skill:

Validate Manifest → Update Dependencies → Build → Compatibility Check → MR

И использовать его с разными Coding Agents.

Но переносимость инструкций не означает одинакового поведения моделей.

И не означает, что Skill автоматически получает доступ к GitLab, Nexus или секретам.

Поэтому:

**Skill ≠ Tool**

**Skill ≠ Permission**

**Model Context ≠ Secret Store**

Для Platform Engineering это довольно полезная модель.

Можно начать создавать каталог внутренних Skills:

— Release Skill
— Dependency Update Skill
— Compatibility Review Skill
— Architecture Review Skill
— CI Investigation Skill

У каждого будут владелец, версия и эталонные проверки.

Это не новый стандарт недели, а практическое развитие уже существующего подхода.

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** можно применять

**3. FlowPlan — Coding Agents могут тратить значительно меньше токенов**

9 ноября опубликовано исследование FlowPlan.

Авторы предложили изменить способ, которым Coding Agent исследует и исправляет код.

Обычный агент часто работает так:

Read Code → Reason → Edit → Read Again → Test → Repeat

Проблема — дорогое повторное чтение и анализ исходников.

FlowPlan предлагает сначала строить структурное представление программы:

— Control Flow Graph
— Data Flow Graph

Затем агент определяет место ошибки и описывает, как должен измениться граф программы.

После редактирования кода он сравнивает фактическую структуру с запланированной.

Workflow:

Source Code → Program Graph → Planned Change → Code Edit → Graph Verification → Tests

Результаты экспериментов довольно интересные.

Для Claude Haiku 4.5 расход токенов относительно обычного агента составил:

— SWE-bench Pro: 46–47%
— SWE-bench Verified: 32–35%
— SecBench: 68–74%

То есть на некоторых задачах расход токенов сократился примерно втрое.

При этом авторы не обнаружили статистически значимого изменения доли решённых задач в шести проверенных конфигурациях.

Но важно: структурная проверка не заменяет обычные тесты.

И результаты пока получены в рамках исследовательских benchmark.

Практический смысл особенно интересен для больших C++-репозиториев.

Вместо того чтобы каждый раз передавать агенту множество файлов, можно предоставлять компактное структурное представление затронутых функций и зависимостей.

**Code Context ≠ Raw Source Dump**

⭐ **Практическая ценность:** 5/5
🧪 **Зрелость:** эксперимент

**4. GitHub — AI Security Scan становится управляемой политикой**

13 ноября GitHub добавила управление AI Scan через REST API.

Теперь настройки AI-сканирования можно включать и отключать централизованно для организации и репозиториев.

Функция пока в public preview.

На первый взгляд небольшое обновление.

Но для Platform Engineering здесь важен архитектурный принцип.

AI Security Review становится частью управляемой инфраструктуры разработки.

Например:

Repository Classification → Security Policy → AI Scan → Findings → Triage → Merge Gate

Для разных классов репозиториев можно применять разные требования.

— Внутренние инструменты: обычный статический анализ.
— Прикладные сервисы: статический анализ и AI Scan.
— Критичные библиотеки: AI Scan и обязательное человеческое ревью.

Это пример собственной политики, не готовая схема GitHub.

Важно, что AI Scan не должен заменять детерминированные проверки безопасности.

**AI Review ≠ Security Guarantee**

**💡 Что можно попробовать**

**1. Agent Autonomy Ladder**

Для одного внутреннего агента определить четыре уровня самостоятельности.

Начать с чтения и рекомендаций.

Разрешать запись только после проверки качества на эталонных задачах.

Результат — контролируемое внедрение вместо выдачи всех полномочий сразу.


**2. Versioned Platform Skills**

Создать первый общий Skill для обновления платформенных библиотек.

Вынести в него проверки версий, сборки и совместимости.

Обновлять через MR.

Результат — единый повторяемый процесс для разных агентов.


**3. Skill Contract Tests**

Подготовить 10–15 эталонных задач.

После обновления Skill запускать:

Skill Update → Evaluation → Compare Baseline → Approve

Результат — возможность обнаруживать деградацию поведения агента.


**4. AI Security Policy as Code**

Классифицировать репозитории по критичности.

Назначить обязательные проверки для каждого класса.

Не позволять агенту самостоятельно отключать эти проверки.

Результат — управляемая безопасность AI-разработки.


**5. Graph-guided Coding PoC**

Выбрать 10–20 типовых задач исправления C++-кода.

Сравнить обычный Coding Agent с подходом, использующим графы управления и данных.

Измерять:

— стоимость токенов;
— время решения;
— успешность сборки;
— прохождение тестов;
— полноту исправления.

Результат — понимание, даёт ли структурный контекст экономию именно на вашей кодовой базе.


**Главный вывод недели**

AI Engineering постепенно переходит от вопроса «что умеет агент?» к вопросу «при каких условиях ему можно доверять?».

Skills делают инженерные процессы повторно используемыми.

Структурный контекст может уменьшать стоимость выполнения.

А независимые проверки и политики определяют, какие результаты можно принимать и какие действия разрешать.

Целевая цепочка:

Requirements → Readiness Gate → Versioned Skill → Coding Agent → Independent Verification → Policy → Merge

**Хорошая Agent Platform — это не просто набор сильных моделей. Это управляемая система исполнения инженерных процессов.**
